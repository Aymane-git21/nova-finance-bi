# SAP HANA layer

Layered modeling on **SAP HANA, express edition** — local Docker, permanent, no trial clock. **Phase 3.** The landscape moved here from HANA Cloud after BTP proved unreachable; see [ADR-002](../docs/adr/002-fully-local-landscape.md).

## Quick start

```bash
./hana/hxe.sh init && ./hana/hxe.sh start
```

```bash
python hana/load_data.py && python hana/deploy_views.py
```

First boot takes several minutes; `start` waits until the tenant actually accepts SQL rather than until the container reports running. Those are not the same moment, and treating them as one is how a loader fails against a perfectly healthy database.

| Command | Does |
|---|---|
| `./hxe.sh init` | Generate the master password and seed it into the data volume |
| `./hxe.sh start` | Bring the database up and wait for SQL |
| `./hxe.sh stop` | Stop the container, keep the data |
| `./hxe.sh status` | Container state, uptime, memory, volume location |
| `./hxe.sh sql` | Interactive `hdbsql` session on the HXE tenant |
| `./hxe.sh logs` | Follow the container log |
| `./hxe.sh destroy` | Remove the container **and** the data volume (asks for confirmation) |

Credentials are generated by `init`, written to `hana/.hxe-credentials` at mode 600, and excluded by `.gitignore`. Nothing is hardcoded and no password reaches the repository. The loader and the deployer read from that file or from `$HXE_MASTER_PASSWORD`.

## Operational note

None of the HANA Cloud free-tier burden applies here: no nightly auto-stop, no 30-day deletion rule, no expiry. `hxe.sh start` exists for the beginning of a working session, not as a survival mechanism — which is why the roadmap's `start-instance.sh` and the risk-register row about losing the whole model to a deletion timer are both gone.

What replaces them is RAM. The server-only image needs **8 GB minimum, 12 recommended**, and this machine has 19.3 GB total. Closing browsers and chat clients before starting is a real prerequisite, not a nicety. The full image with XS Advanced needs 16–24 GB and does not fit — hence no browser-based calculation-view editor, and hence L3 authored as design-time artifacts.

## Layers

| Layer | Schema | Contents | BW/4HANA analogue |
|---|---|---|---|
| **L1 RAW** | `NOVASPACE_L1` | 1:1 views on the loaded tables. Projection and typing only | Staging / inbound ADSO |
| **L2 HARMONISED** | `NOVASPACE_L2` | Signed amounts, manual/late flags, currency translation at both rate types, master-data joins, working-day arithmetic | Standard ADSO with transformations |
| **L3 REPORTING** | `NOVASPACE_L3` | Star-joined reporting views with cube semantics and restricted key figures, plus the run-rate table function | CompositeProvider + BEx query elements |

Full object-by-object mapping: [`../docs/bw4hana-mapping.md`](../docs/bw4hana-mapping.md).

L1 adds nothing but a stable column contract, and that restraint is the point: when a number is wrong, L1 is the layer you can rule out without reading it, because there is nothing in it to be wrong.

### L3 objects

| Object | Serves |
|---|---|
| `CV_PL_ACTUALS` | KPI-02 — P&L by entity, period and account group, with manual and late counts as restricted key figures |
| `CV_BUDGET_VARIANCE` | KPI-04 — actual against evenly-phased budget. `FULL OUTER JOIN`, so spend without budget and budget without spend both survive |
| `CV_CLOSE_MONITOR` | KPI-01 and KPI-03 — the close checklist joined to the same period's postings, so the entity that closes late is visibly the one posting by hand |
| `CV_FX_IMPACT` | KPI-06 — the same local amount translated at the actual and the frozen budget rate, plus gross exposure |
| `CV_IC_RECONCILIATION` | KPI-08 — unordered entity pairs netted, with materiality applied in the view |
| `TF_PROGRAMME_RUNRATE` | KPI-05 — rolling run-rate and naive EAC, SQLScript table function with a window function |

## The relationship to the Python

[`../data-generator/novaspace/harmonise.py`](../data-generator/novaspace/harmonise.py) implements the same L2 logic and all eight KPIs in Python, with a test suite behind it. It is the **reference implementation**: any disagreement between it and the SQL here is a defect in the SQL, not a difference of opinion.

That is not redundancy for its own sake. Having the expected answer computed independently, from the same seeded dataset, turns "does the view agree" into something checkable. Without it, a subtly wrong `JOIN` produces a number that looks plausible and nothing ever contradicts it.

## `TF_PROGRAMME_RUNRATE` and the ABAP question

An AMDP is an ABAP class method whose body is SQLScript, pushed down and executed by HANA. The ABAP layer is the wrapper; **HANA does the work**.

So the interesting part of Phase 4 — the window function, the ranking, the rolling aggregation — lives in [`sql/04_runrate_function.sql`](sql/04_runrate_function.sql), runs for real, and gets benchmarked in Phase 7. `ZCL_AMDP_RUNRATE` in [`../abap/`](../abap/) wraps this identical body and is labelled `NOT ACTIVATED`, because no ABAP system was reachable. The pushdown logic is proven; the wrapper is source-only. Reasoning: [ADR-003](../docs/adr/003-abap-evidence-strategy.md).

## Layout

| Path | Contents |
|---|---|
| `docker-compose.yml` | The HXE container: ports, sysctls, ulimits, health check |
| `hxe.sh` | Lifecycle: init, start, stop, status, sql, logs, destroy |
| `load_data.py` | `hdbcli` loader — explicit DDL, batched `executemany`, reads counts back from the database |
| `deploy_views.py` | Runs `sql/*.sql` in layer order, with a splitter that understands SQLScript `BEGIN`/`END` |
| `sql/01_l1_raw.sql` | L1 views |
| `sql/02_l2_harmonised.sql` | L2 views |
| `sql/03_l3_reporting.sql` | L3 reporting views |
| `sql/04_runrate_function.sql` | The run-rate/EAC table function |

Types in `load_data.py` are declared, never inferred. An inferred load turns `company_code` into an integer the moment every value happens to be numeric, drops leading zeros, and stores money as a float — and the first two surface much later as a join returning no rows. Column widths were measured against the generated data, which is how `department_id` was caught at 11 characters against a declared `NVARCHAR(10)`.
